# gitops/tenants - tenants and the service versions they run

Everything about a tenant is a directory here. Two ApplicationSets
(`gitops/apps/applicationsets/`) turn the files into Argo CD Applications; nobody runs `kubectl` or `helm` by hand.

```
gitops/tenants/
├── _template/                      copied when onboarding (excluded from both generators)
├── acme/                           dedicated tier, canary ring "early"
│   ├── tenant.yaml                 -> Application tenant-acme       (charts/tenant, wave 10)
│   ├── values-microservice.yaml    tenant-wide overrides for all its microservice releases
│   ├── values-frontend.yaml        tenant-wide overrides for its frontend releases
│   ├── configmaps/                 plain ConfigMaps (Ansible k8s_configmaps output), synced by tenant-acme
│   └── services/
│       ├── orders-v1.yaml          -> Application acme-orders-v1    (charts/microservice, wave 20)
│       ├── orders-v2.yaml          -> Application acme-orders-v2    (v1 + v2 side by side: migration)
│       ├── payments-v1.yaml        (image pinned during a change freeze)
│       ├── catalog-v1.yaml
│       └── web-v1.yaml             -> Application acme-web-v1       (charts/frontend)
├── globex/                         dedicated tier, canary ring "canary" (first to get every image)
│   └── services/ orders-v2, payments-v1, catalog-v2 (early access)
├── initech/                        shared tier: NO services/ - served by the pool in shared-services
└── shared/                         the pool itself: landing zone "shared-services" + pooled releases
    └── services/ orders-v1, orders-v2, payments-v1, catalog-v1, web-v1
```

| Tenant | Tier | Namespace | API host | Services (pinned versions) |
|--------|------|-----------|----------|----------------------------|
| `acme` | dedicated | `tenant-acme` | `acme.api.example.com` | orders v1 + v2, payments v1 (pinned 1.11.4), catalog v1, web v1 |
| `globex` | dedicated | `tenant-globex` | `globex.api.example.com` | orders v2, payments v1, catalog v2 |
| `initech` | shared | (pooled in `shared-services`) | `api.example.com` | whatever the pool runs |
| `shared` | pool | `shared-services` | `api.example.com` | orders v1 + v2, payments v1, catalog v1, web v1 |

## File formats

### `tenant.yaml`

Top-level keys are generator parameters. All of them must be present (the ApplicationSets use
`missingkey=error`):

| Key | Meaning |
|-----|---------|
| `name` | tenant id = directory name (lowercase DNS label, <= 20 chars) |
| `displayName` | human readable |
| `tier` | `dedicated` or `shared` |
| `environment` | `production`, `staging`, ... |
| `namespace` | `tenant-<name>` (dedicated) or `shared-services` (shared / pool) |
| `releaseRing` | `canary` / `early` / `general` (label on the tenant Application) |
| `quota` | namespace ResourceQuota summary (charts/tenant `quota`) |
| `values` | any charts/tenant values; deep-merged over the keys above and passed as `helm.valuesObject` |

### `services/<service>-<version>.yaml`

One file per deployed service version:

```yaml
service: orders          # gitops/apps/<service>/ must exist
version: v2              # gitops/apps/<service>/values-<version>.yaml must exist
language: dotnet         # dotnet | java | python | static (label)
chart: microservice      # microservice | frontend  -> charts/<chart>
ring: early              # optional, default general: progressive-sync step (canary -> early -> general)
imageTag: "2.4.1"        # optional pin; otherwise image.tag from values-<version>.yaml (bumped by CI)
replicas: 4              # optional minimum replicas (replicaCount + HPA/KEDA minReplicas)
values: {}               # optional chart overrides (highest precedence)
```

The ApplicationSet adds the tenant wiring for you: `tenant`, `service.name/version`, `kong.host`
(`<tenant>.api.example.com`, or `api.example.com` for the pool), database/user `<tenant>_<service>`,
RabbitMQ vhost `<tenant>` and user `<tenant>-<service>`, Kafka prefix `<tenant>.`, Redis key prefix
`<tenant>:<service>:`. The frontend chart gets `hosts`, `runtimeConfig.apiBaseUrl/authUrl/tenantId`.

### `values-microservice.yaml` / `values-frontend.yaml`

Tenant-wide overrides applied to every release of that chart for the tenant (e.g. the tenant's Redis
logical DB). **Required** for every tenant that has a `services/` file of that chart (may be `{}`):
the ApplicationSet uses `ignoreMissingValueFiles: false`, so that a missing `values-<version>.yaml` fails
loudly instead of deploying a default image.

### `configmaps/`

Plain Kubernetes manifests synced by the tenant Application into the tenant namespace. Generated by the
Ansible role `k8s_configmaps` (`make configmaps ENV=production MODE=gitops`), reviewed in the PR like any
other change. Keep at least `tenant-feature-flags.yaml`: Argo CD reports a ComparisonError for a directory
source whose path does not exist. Pooled tenants live in `shared-services`, so their ConfigMaps must be
prefixed `tenant-<name>-` to avoid collisions.

## Onboarding a tenant

1. `cp -r gitops/tenants/_template gitops/tenants/newco` and replace every `CHANGE-ME` (`grep -r CHANGE-ME gitops/tenants/newco`).
2. Pick the tier. Dedicated: size `quota`, choose a free Redis DB (acme=1, globex=2, ...) and mirror it in
   `values-microservice.yaml`; keep one `services/<svc>-<version>.yaml` per version the tenant consumes.
   Shared: set `tier: shared`, `namespace: shared-services`, delete `services/`, the `values-*.yaml` files
   and all `data.*` blocks except `redis.keyPrefix`; rename the ConfigMap to `tenant-newco-feature-flags`.
3. Prerequisites outside Git (seed them before merging):
   - Keycloak realm `newco` with groups `newco-admins`, `newco-devs`, `newco-viewers` and a `tenant` claim mapper.
   - Vault: `secret/tenants/newco/<service>` (`DB_PASSWORD`, `RABBITMQ_PASSWORD`, `RABBITMQ_URI` for payments,
     `KAFKA_PASSWORD`, `REDIS_PASSWORD`), `secret/tenants/newco/common`, `secret/tenants/newco/keycloak`
     (`realm_public_key`), Vault Kubernetes-auth role `tenant-newco` (see charts/tenant/README.md).
   - Object storage (`values.data.objectStorage.enabled`, required when the tenant deploys catalog, which mounts the
     static volume `product-images`): Vault `secret/tenants/newco/storage` (`S3_ACCESS_KEY=newco`,
     `S3_SECRET_KEY=<random>`). Buckets, MinIO user and policy are created by the tenant Application.
   - DNS: `newco.api.example.com` and `newco.app.example.com` -> Kong public VIP (dedicated tier).
4. Optionally render ConfigMaps: `make configmaps ENV=production`.
5. Open a PR. After merge, `tenant-newco` (wave 10) creates the landing zone, databases, vhost, topics and
   users; then each `newco-<service>-<version>` Application deploys (retrying until the namespace exists).

## Pinning and upgrading versions

- **New image of a version you already run**: nothing to do - CI bumps `gitops/apps/<svc>/values-<version>.yaml`
  and the services ApplicationSet rolls it out ring by ring; inside each release Argo Rollouts runs a canary
  with Prometheus analysis.
- **Freeze a tenant on an image**: set `imageTag:` in its descriptor (see `acme/services/payments-v1.yaml`).
  Remove the line to follow the version's current tag again.
- **Adopt a new major version**: add `services/<svc>-<new>.yaml` next to the old one. Both run side by side
  (`/<svc>/v1` and `/<svc>/v2`). When the tenant's clients have moved, delete the old file.
- **Downgrade**: pin `imageTag` to the previous tag (or revert the CI bump commit for all tenants).

## Canary per tenant

Three levels, from coarse to fine:

1. **Ring** (`ring:` in the descriptor, `releaseRing:` in tenant.yaml): the services ApplicationSet uses a
   RollingSync strategy - `canary` releases sync first and must be Healthy before `early` (50% at a time) and
   `general` (25% at a time) follow. Put a tenant in the canary ring by setting `ring: canary` on its descriptors.
2. **Early-access major**: only the tenants that should try `catalog v2` get `catalog-v2.yaml` (globex).
3. **In-release canary**: each release is an Argo Rollout; tune it per tenant through `values.rollout.canary`
   (e.g. stricter analysis for globex catalog v2).

## Decommissioning a tenant

1. Remove the tenant's `services/*.yaml` (Kong routes disappear; data untouched). Merge, wait for the
   releases to be deleted.
2. Export/backup the data (CNPG backup of the `<tenant>_*` databases, Kafka topic retention, RabbitMQ DLQ).
3. In `tenant.yaml` set `values.tenant.protectNamespace: false`; merge.
4. Delete the tenant directory; merge. Argo CD deletes `tenant-<name>` including the namespace, the vhost,
   Kafka topics/users and the Kong consumer. CNPG databases use `databaseReclaimPolicy: retain`: drop them
   manually after the retention period (`DROP DATABASE <tenant>_<db>; DROP ROLE <tenant>_<db>;`).
   MinIO buckets `<tenant>-*` and the MinIO user/policy are kept as well (static PVs are deleted with the
   Application, their bucket data is untouched); after the retention period: `mc rb --force minio/<tenant>-<bucket>`,
   `mc admin user rm minio <tenant>`, `mc admin policy rm minio <tenant>-rw`.
5. Remove `secret/tenants/<name>`, the Vault role, the Keycloak realm and DNS records.
