# Resilience: timeouts, retries, circuit breakers, startup & sidecar containers

Resilience is layered. Each layer has a **budget**, and outer layers always have a larger timeout
than inner layers so retries never outlive the caller.

| Layer | Timeout | Retries | Circuit breaker | Configured in |
|-------|---------|---------|-----------------|---------------|
| Client → Kong | 60 s (Kong `read_timeout`) | none (non-idempotent safe) | — | `gitops/platform/core/kong` |
| Kong → service (mesh) | route timeout (default 10 s) | 3 attempts, 3 s per try, on `5xx,reset,connect-failure,refused-stream,gateway-error` | outlier detection: eject host after 5 consecutive 5xx for 30 s, max 50% | `charts/microservice` → `istio.*` |
| Service → service (mesh) | same `VirtualService` of the callee | same | same `DestinationRule` of the callee | `charts/microservice` |
| Application → dependency | Polly / Resilience4j / tenacity per call (1–3 s) | jittered exponential backoff, max 3 | app-level breaker (50% failure over 30 s → open 15 s) | `services/*` |
| Connection pools | `connectionPool.tcp.connectTimeout: 2s` | — | `http1MaxPendingRequests` / `http2MaxRequests` = bulkhead | `charts/microservice` |
| Rate limits | — | — | Kong per consumer/tenant (Redis) | `charts/microservice` → `kong.rateLimit` |

**Retry storms**: only one layer should retry a given hop aggressively. Mesh retries cover transient network
errors; application retries are limited to idempotent operations and honour `Retry-After`.
Kafka producers use idempotence; RabbitMQ consumers use manual acks, redelivery limits and DLQs.

## Circuit breaking in Istio

```yaml
trafficPolicy:
  connectionPool:
    tcp: { maxConnections: 2000, connectTimeout: 2s }
    http: { http1MaxPendingRequests: 2000, http2MaxRequests: 4000, maxRetries: 10 }
  outlierDetection:
    consecutive5xxErrors: 5
    consecutiveGatewayErrors: 5
    interval: 10s
    baseEjectionTime: 30s
    maxEjectionPercent: 50
```

Ejections are visible in Grafana (*Circuit breakers & retries* dashboard) and alert via
`envoy_cluster_outlier_detection_ejections_active`.

## Startup containers (init containers)

Every pod generated by `charts/microservice` gets:

1. `wait-for-<dependency>` init containers for each enabled dependency (Postgres, Redis, RabbitMQ, Kafka) —
   they block until the endpoint accepts TCP connections (bounded by a timeout) so the app never crash-loops
   on cold cluster starts.
2. An optional `migrations` init container (same image, idempotent migration command).
3. For Java with APM enabled, an init container copying the OpenTelemetry Java agent into a shared volume.

Probes: `startupProbe` (`/health/startup`, up to 150 s) gates liveness; `livenessProbe` only checks the
process; `readinessProbe` checks dependencies and removes the pod from load balancing when they fail.

## Sidecar containers

- **istio-proxy** (always, via namespace injection; `holdApplicationUntilProxyStarts: true`).
- Optional `sidecars:` in chart values (e.g. nginx-prometheus-exporter for the frontend, protocol adapters).
- Graceful shutdown: `preStop` sleep 5 s, `terminationGracePeriodSeconds: 30`; apps drain in-flight requests on SIGTERM;
  Istio `EXIT_ON_ZERO_ACTIVE_CONNECTIONS` lets the proxy drain last.

## Availability controls

PodDisruptionBudgets (min 50%), topology spread across zones/hosts, PriorityClasses (`platform-critical`,
`data-critical`, `apps-high`, `apps-default`, `batch-low`), HPA with fast scale-up / slow scale-down,
and Argo Rollouts automatic abort on failed canary analysis.
