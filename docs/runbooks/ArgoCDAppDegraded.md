# ArgoCDAppDegraded

Also used by `ArgoCDAppMissing` (`gitops/platform/observability/alerts/manifests/platform-rules.yaml`).

## Severity

| Alert | Severity | Expression | `for` |
|---|---|---|---|
| `ArgoCDAppDegraded` | warning | `max by (name, project, dest_namespace) (argocd_app_info{health_status="Degraded"}) == 1` | 15m |
| `ArgoCDAppMissing` | warning | `max by (name, project) (argocd_app_info{health_status="Missing"}) == 1` | 30m |

Both carry `namespace: argocd`.

## Meaning

Argo CD's health assessment of Application `{{ $labels.name }}` has been `Degraded` for 15 minutes
(a managed resource is unhealthy: Deployment/StatefulSet not available, Rollout degraded/aborted, PVC pending,
CR reporting an error) or `Missing` for 30 minutes (resources expected from Git do not exist).

Application names: platform components use the directory name (`kong`, `longhorn`, `postgres`, `elastic`,
`kube-prometheus-stack`, ...; projects `core` / `data` / `observability`), category apps `platform-core`,
`platform-data`, `platform-observability`, `tenants-and-apps`, and service releases are
`<tenant>-<service>-<version>` (e.g. `acme-orders-v1`, project `apps`) generated by the `services`
ApplicationSet.

## Impact

Depends on the resource. For service releases, a Degraded application also **halts the ApplicationSet
RollingSync** (canary → early → general rings): the next ring is not updated until it is Healthy.

## Diagnosis

```bash
argocd login argocd.ops.example.local --sso
argocd app get <name> --show-operation               # tree with health per resource
argocd app resources <name> | grep -v Healthy
kubectl -n argocd get application <name> -o jsonpath='{.status.health}{"\n"}'
kubectl -n <dest_namespace> get events --sort-by=.lastTimestamp | tail -30
```

Or the UI `https://argocd.ops.example.local` → application → filter *Health: Degraded*.

Common cases:

- **Rollout Degraded** (`acme-orders-v1`): canary aborted → see [RolloutAborted](RolloutAborted.md).
- **Pods CrashLoopBackOff / not Ready**: `kubectl -n <ns> describe pod`, logs, and readiness dependencies
  (DB/Redis/broker) — see [high-error-rate](high-error-rate.md#podrestarts).
- **PVC Pending**: Longhorn cannot schedule → [LonghornNodeStorageAlmostFull](LonghornNodeStorageAlmostFull.md).
- **ExternalSecret SecretSyncedError**: Vault path missing / ESO auth →
  `kubectl -n <ns> describe externalsecret <name>`, `kubectl get clustersecretstore vault-backend`.
- **Operator CR unhealthy** (CNPG `Cluster`, `Kafka`, `RabbitmqCluster`, `Elasticsearch`): follow the component
  runbook (`gitops/platform/data/README.md#runbooks`, Elasticsearch runbooks here).
- **Missing**: a resource is excluded by the AppProject whitelist, pruned by another app, or a sync never
  completed — `argocd app diff <name>`.

## Mitigation

1. Fix the underlying resource through Git (image, values, CR spec). Avoid `kubectl edit` on managed objects:
   `selfHeal: true` reverts manual changes.
2. For a bad service release: abort/rollback the Rollout and revert the image tag commit
   (`gitops/apps/<service>/values-<version>.yaml`) or pin `imageTag` in
   `gitops/tenants/<tenant>/services/<service>-<version>.yaml`.
3. Transient issue already fixed: `argocd app get <name> --hard-refresh`; restart the stuck workload
   (`kubectl -n <ns> rollout restart deploy/<name>` or `kubectl argo rollouts restart <name> -n <ns>`).
4. `Missing` after a failed sync: `argocd app sync <name>` and read the operation result
   ([ArgoCDAppOutOfSync](ArgoCDAppOutOfSync.md)).

## Escalation

`#platform-alerts`. Service releases: the owning service team / tenant channel. Platform components: platform
on-call; data components: data team (`team=platform-data`).
