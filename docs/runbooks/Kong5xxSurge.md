# Kong5xxSurge

Also used by `KongGlobal5xxRateHigh` (`gitops/platform/observability/alerts/manifests/edge-rules.yaml`).

## Severity

| Alert | Severity | Condition | `for` |
|---|---|---|---|
| `Kong5xxSurge` | critical | > 5 % 5xx for one Kong `service`, and > 1 rps | 5m |
| `KongGlobal5xxRateHigh` | warning | > 2 % 5xx across the whole gateway | 5m |

Both carry `namespace: kong`.

## Meaning

From the Kong `prometheus` plugin (`KongClusterPlugin` `global-prometheus`, `status_code_metrics: true`):

```promql
(sum by (service) (rate(kong_http_requests_total{code=~"5.."}[5m]))
  / sum by (service) (rate(kong_http_requests_total[5m]))) > 0.05
and sum by (service) (rate(kong_http_requests_total[5m])) > 1
```

`service` is the Kong service generated by the Kong Ingress Controller from a release's Ingress
(it contains the Kubernetes namespace and Service name, e.g. `tenant-acme` / `orders-v1`). A 5xx can come from
the upstream (the app returned 5xx), from the mesh (Istio sidecar of `kong-gateway` pods: 503 `UH`/`UO`, 504
timeouts) or from Kong itself (502 upstream connect error, 503 no healthy targets).

## Impact

Public API clients on `api.example.com` / `<tenant>.api.example.com` get errors for that route. The global
alert means a gateway-wide problem.

## Diagnosis

1. Grafana **Kong API Gateway** (`https://grafana.ops.example.local/d/kong-gateway`): *5xx ratio by service*,
   *Requests / s by status class*, *Unhealthy upstream targets*, *p99 total latency*.
2. Who generates the 5xx:
   ```promql
   sum by (service, code) (rate(kong_http_requests_total{code=~"5.."}[5m]))
   sum by (service, code, source) (rate(kong_http_requests_total{code=~"5.."}[5m]))   # source=kong|service (Kong 3.x)
   ```
   Then compare with the mesh view of the upstream: Grafana **Microservice RED** for that namespace/service, or
   `sum by (response_code, response_flags) (rate(istio_requests_total{reporter="source", source_workload="kong-gateway",
   destination_service_name="orders-v1"}[5m]))`.
3. Kong proxy logs / access logs:
   ```bash
   kubectl -n kong get pods -o wide
   kubectl -n kong logs deploy/kong-gateway -c proxy --tail=200 | grep -E '" 5[0-9]{2} '
   ```
   Kibana, data view `logs-*-k8s`: `kubernetes.namespace_name : "kong" and response_code >= 500`
   (Kong access log parsed by Fluent Bit); correlate with `correlation_id` in the upstream's logs.
4. Upstream health: pods Ready? `kubectl -n tenant-acme get pods -l app.kubernetes.io/instance=orders-v1`;
   outlier ejections on the *Circuit Breakers & Retries* dashboard.
5. Global surge: check `kong-gateway` pods (restarts, CPU/memory, HPA 3..20), `kong-controller` logs for
   config sync errors, and whether all upstreams fail at once (Istio / DNS / network problem).

## Mitigation

1. Upstream at fault → follow [high-error-rate](high-error-rate.md) / [SLOAvailabilityBudgetBurn](SLOAvailabilityBudgetBurn.md)
   for that release (abort canary, roll back image, fix dependency).
2. Kong-generated 502/503: upstream Service has no ready endpoints or the sidecar rejects (UO overflow) — scale
   the upstream, check its DestinationRule `connectionPool` limits.
3. Kong itself unhealthy (OOM, CPU saturation): `kubectl -n kong rollout restart deploy/kong-gateway`
   (PDB-protected, rolling); raise HPA `maxReplicas` in `gitops/platform/core/kong/values.yaml` if pinned at 20.
4. Bad Kong configuration pushed by an Ingress/KongPlugin change: revert the Git change; the controller
   re-syncs the DB-less config.

## Escalation

Critical → on-call (PagerDuty). Per-service: the owning service team. Global: platform on-call (edge).
